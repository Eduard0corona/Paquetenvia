## Why the Verification Precedes Owner Approval

The verification compares the actual Azure grantor representation against:

```text
ROUTINE_MAP_AI18_PENDING_V1

```

The result can determine whether the declared normative grantor expectation is valid for the Azure managed-service authorization model.

Therefore its result may require a change to the normative contract itself.

That fact must be known before the Owner signs the contract.

Required pre-approval outcome:

```text
E002_ROUTINE_MAP_GRANTOR_PLATFORM_VERIFICATION
=
PASS

```

The Owner-approval gate must not proceed while:

```text
verification = NOT_EXECUTED

```

or:

```text
verification = FAILED

```

If:

```text
observed Azure grantor map
!=
ROUTINE_MAP_AI18_PENDING_V1 declared grantor map

```

the result is:

```text
E002_ROUTINE_MAP_GRANTOR_PLATFORM_MISMATCH
STOP_FOR_CONTRACT_REVIEW

```

The mismatch must be consciously resolved during contract review by adopting an explicit platform-specific normative expectation before Owner approval.

The expected map must not be changed automatically to match observed state.

---

### Purpose of Runtime Reconfirmation

Runtime reconfirmation is mandatory because PostgreSQL catalog state may change between:

```text
Owner approval

```

and:

```text
actual Notifications retry execution

```

Therefore the implementation must prove immediately before retry that the catalog condition relied upon at approval time still holds.

Required:

```text
pre-approval verification = PASS

and

runtime reconfirmation = PASS

```

---

### Runtime Reconfirmation Failure

If step `0b` observes:

```text
Azure AI-18 grantor map
!=
the Owner-approved declared grantor map

```

even when the earlier pre-approval verification passed, the retry must stop.

Failure:

```text
E002_ROUTINE_MAP_GRANTOR_PLATFORM_MISMATCH
STOP_FOR_CONTRACT_REVIEW

```

This failure means:

```text
catalog state or provider-observed authorization representation
changed after contract approval

```

It does not authorize:

```text
automatic map adjustment

automatic ACL repair

automatic privilege repair

Notifications migration execution

```

The retry remains blocked until the inconsistency is reviewed.

---

### Step 0b Blocking Semantics

Step `0b` remains blocking.

Required:

```text

```

Without step `0b` PASS:

```text

=

```

The retry therefore has two temporally distinct grantor checks:

```text

  mutation =
    NONE

  implementation authorization required =

  mutation =
    NONE

    RUNTIME_RECONFIRMATION

```

Both use the same comparison contract.

Both fail with:

```text

STOP_FOR_CONTRACT_REVIEW
```
