En Azure:

```text

```

debe existir **únicamente** en la configuración del:

```text

```

Debe estar ausente de:

```text

Web
API
Worker

Functional Scenario / Acceptance Job

```

No se utilizará environment-level shared opt-in.

Static guard debe verificar esta exclusividad.

DOTNET_ENVIRONMENT=DevSynthetic

# 5. AZR-001-TRACKING-EXCEPTION-001

Este erratum es el **único propietario normativo** del identificador:

```text
AZR-001-TRACKING-EXCEPTION-001

```

Definición:

> Excepción estrecha a la regla API-only de AC-054 que permite exclusivamente al `RLS Verification Job / TrackingVerify` invocar `IPublicTrackingTokenService.RotateAsync` porque TRK-001 no expone una API administrativa para emitir o rotar tokens públicos.

La excepción permite únicamente:

```text
TrackingVerify
→ IPublicTrackingTokenService.RotateAsync

```

con runtime credential.

No autoriza:

```text
privileged SQL
other direct business mutations
seed SQL
new HTTP management API
general job-based application writes

```

SEC-003 puede referenciar esta excepción, pero no redefinirla.

# 7. Tenant-aware token mutation

TrackingVerify proporciona:

```text
synthetic ActorId
principal OrganizationId
eligible OrderId
unique RequestId

```

El núcleo SEC-003 reutiliza:

```text
IPublicTrackingTokenService.RotateAsync

```

que debe continuar entrando por:

```text
TenantTransactionContext<OrdersDbContext>

```

con secuencia canónica:

```text
BEGIN
→ app.current_user_id
→ app.current_org_ids
→ SET LOCAL ROLE paqueteria_app
→ mutation
→ canonical audit
→ COMMIT

```

El verifier no aplica estos comandos por su cuenta.

---

# 8. Public projection path

Para fallback no HTTP, TrackingVerify deberá utilizar el reader productivo:

```text
IPublicTrackingProjectionReader

```

cuya implementación PostgreSQL ejecuta semánticamente:

```text
BEGIN
→ SET LOCAL ROLE paqueteria_app
→ security.get_public_tracking_projection(token)
→ COMMIT

```

No establece:

```text
app.current_user_id
app.current_org_ids

```

porque la proyección pública es anónima y token-derived.

Por tanto, el fallback no deberá añadir tenant context artificialmente.

---

# 9. Phase H repeatability

Una sola ejecución de:

```text
Phase H / TrackingVerify

```

debe realizar dos rotaciones consecutivas sobre la misma orden.

```text
A:
RotateAsync
→ token A
→ verification A

B:
RotateAsync same order
→ token B
→ verification B

```

La segunda ejecución **no** se difiere a:

```text
AC-047 reset
a later workflow
manual rerun

```

Es parte del PASS de AC-033 en la misma aceptación.

Cuando sea verificable:

```text
token A becomes invalid after B
token B remains valid

```

Los plaintext permanecen sólo en memoria.

# 11. Verification coverage

## FULL_HTTP_ENDPOINT

Si el RLS Verification Job puede alcanzar autorizadamente:

```text
GET /api/v1/tracking/{token}

```

por el endpoint desplegado:

```text
verificationCoverage=FULL_HTTP_ENDPOINT

```

Esto prueba:

```text
ingress/network path
HTTP routing
endpoint middleware/pipeline
token lookup
public projection
response serialization

```

además del issuer.

## PROJECTION_CONTRACT_ONLY

Si el resolved network mode impide ese HTTP path:

```text
verificationCoverage=PROJECTION_CONTRACT_ONLY

```

TrackingVerify consume el token mediante:

```text
IPublicTrackingProjectionReader

```

contra PostgreSQL Azure.

Esto prueba el contrato productivo de acceso anónimo a proyección:

```text
runtime LOGIN
SET LOCAL ROLE paqueteria_app
security.get_public_tracking_projection(token)
projection parsing/domain contract

```

No prueba:

```text
Container Apps ingress for tracking request
HTTP route mapping
tracking HTTP middleware
request/response transport
deployed endpoint serialization pipeline

```

Por tanto la diferencia no es tenant context: **el fallback reproduce el mismo modelo anónimo de lookup de base de datos, pero omite toda la superficie HTTP desplegada**.
